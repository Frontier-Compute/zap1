what this is for

Receipts for work that machines claim to have done.

Automated systems report what they did, and those reports are normally trust-me claims. A ZAP1 bundle lets an outsider recompute whether a supplied leaf is included in a supplied root. It does not prove the underlying event happened.

a

Agent actions

Agents submit registration, policy, and action claims. Public bundles expose the leaf hash and path while withholding stored subject preimages. Inclusion does not attest model identity, authorization, execution, or policy compliance.

b

Evaluation verdicts

The applicant-published inspect-receipts package emits bounded commitments containing hashes, metrics, and coarse identifiers. Its offline checker returns MATCH or MISMATCH against a disclosed eval log. It does not prove the verdict is correct.

c

Lifecycle and payment claims

Operator-issued ownership, deployment, hosting-payment, and paid-access claims become Merkle receipts. Public bundles withhold stored subject fields. Inclusion does not establish that the claimed event occurred or that the operator's records are complete.

Recompute the March 27 in-window proof fixture in under a minute:

curl -s https://raw.githubusercontent.com/Frontier-Compute/zap1/59279222584e490f099a2f358c248cab5e800466/examples/live_ownership_attest_proof.json -o proof.json
python verify_proof.py --proof proof.json --allow-historical-legacy

The successful historical-legacy branch reports MERKLE MATCH for inclusion under the supplied pre-fix root, followed by its typed-witness and legacy-root warnings. The verifier script ships at the repo root and re-walks the downloaded bundle locally. The fixture carries an API-recorded transaction reference, but encrypted memo binding is not independently verified.

Scope, stated plainly Check /anchor/status for the current root's publication state. Historical API records list legacy roots with Zcash transaction IDs, and transaction existence is independently checkable. Orchard memo contents are encrypted, so independently binding a listed root to a transaction memo requires a separate disclosure artifact that is not currently published. Neither a Merkle proof nor a transaction proves the underlying event claim is true.
how the proof moves

The review path is short on purpose.

This page is generated by the ZAP1 API and pulls aggregate counts from the same database that serves /stats.

01

Commit an event

Applications submit typed operator claims. The service stores the submitted fields, while public feeds and proof bundles withhold stored wallet and serial preimages.

02

Hash the leaf

ZAP1 commits event material into BLAKE2b leaf hashes with stable type semantics.

03

Record a transaction reference

The current root binds the leaf count. Historical roots are recorded with Zcash transaction IDs for independent transaction lookup; their encrypted memo contents require separate disclosure material for independent root-to-transaction verification.

04

Publish proofs

Proof bundles expose inclusion material, anchor metadata, and machine-readable verifier input.

05

Verify offline

The zap1-verify crate and verify_proof.py re-walk supplied Merkle proofs locally. Python, Rust, and TypeScript implementations are checked against a shared equivalence corpus. This verifies proof consistency, not encrypted memo contents.
